触发：`travel-apply-list` 返回空列表。

```
<<<VISIT_BLOCK_V1>>>{"protocol":"visit.session.v1","type":"a2ui.render","card":{"card_name":"create-travel-info-card","schema_version":"1.0","data":{"travelApplyNo":""},"action_states":{"create_travel_info":{"enabled":true,"visible":true}}}}<<<END_VISIT_BLOCK_V1>>>

前端行为：用户填写差旅单号后点击"创建差旅信息"，前端转成自然语言消息发给 Agent。Agent 提取单号 → `batch-resolve travel_apply_no=<单号>` → 继续流程。

```
<<<VISIT_BLOCK_V1>>>{"protocol":"visit.session.v1","type":"a2ui.render","card":{"card_name":"create-business-license-card","schema_version":"1.0","data":{"licenseName":""},"action_states":{"create_business_license":{"enabled":true,"visible":true}}}}<<<END_VISIT_BLOCK_V1>>>

前端行为：用户填写营业执照名称后点击"创建"，前端转成自然语言消息发给 Agent。Agent 提取 `licenseName` → `batch-resolve visit_object_info=<licenseName>` → 继续流程。

## [ambiguous 候选] — pending_ambiguous_slot 非空时纯自然语言输出

**禁止输出任何卡片协议块**。一次只展示一个槽位的候选，禁止同时选客户+地址。用户回序号后，batch-resolve 的 `raw` 必须是对应候选完整名称（或 poiId），禁止传 `"1"`。

> 术语屏蔽、处理过程屏蔽、槽位确认记录屏蔽统一由 SKILL.md「🔴 输出前强制扫描」红线约束，本节不再重复。

### 输出格式模板（强制，违反即整条重写）

**整条回复 = 首行提示语 + 候选列表 + 末尾提示语，三部分按下方模板照填，禁止增减任何字符。**

> **🔴 首字符硬校验（违反即整条作废重写）**：
> - 模板 A/B/C 首字符必须是 `找`（`找到多个匹配的...`）
> - 模板 D 首字符必须是 `请`（`请问该客户是新客还是老客？`）
> - **若回复首字符不是 `找` 或 `请`** → 说明首行前加了"pendingAmbiguousSlot 为...""visit_object_info 有...""根据 skill 指令..."等内部话术 → 整条作废，从模板首行重新输出
> - **禁止任何前言/开场白/状态描述**：`pendingAmbiguousSlot 为 visit_object_info（门店），需要先展示门店候选列表。` / `visit_object_info 有多个候选，需要先解决。` / `根据 skill 指令展示候选：` / `现在处理这个槽位。` 等全部禁止，直接从模板首行开头

#### 模板 A — 客户候选（visit_object_info，类型为 ad_customer/agent/provider）

> ⛔ **整条回复第一个字必须是「找」**，前面不能有任何字符（包括空格、换行、说明文字）。
> **若第一字不是「找」** → 说明首行前混入了 `pendingAmbiguousSlot 为 xxx` 等内部话术 → **删掉前面所有内容，从「找到多个匹配的客户」重新开始写**。

首行固定：`找到多个匹配的客户，请选择：`
候选每行格式：`{序号}. {corporationName}（{regCity}）`，**每项必须独占一行**，带序号 `1.` `2.` ...
- `regCity` 仅在有值时显示，无值时只输出 `{序号}. {corporationName}`，括号省略
末行固定（单独一行）：`请回复序号，或输入更精确的名称重新搜索`

> **🔴 每项必须独占一行，禁止合并到一行**。候选项之间用换行符 `\n` 分隔，不是空格。输出前检查：每个候选必须以 `序号.` 开头单独成行。

### 格式红线

- **整条回复只能是上述四个模板之一**，禁止首行自拟、禁止末行自拟、禁止候选行加任何额外字符
- **禁止输出思考过程**：首行前不得有"我找到了""现在需要""有两个字段""根据"等任何说明文字，直接以模板首行开头
- **禁止候选行带类型标签**（如"广告客户"/"代理商"/"团购服务商"等）
- **候选 100% 来自 `candidatesJson`**，禁止凭记忆编造。若 `candidatesJson` 为空，追问用户「请提供更精确的名称」

### 用户回选后的 raw 映射

| 候选类型 | 用户选择后 `raw` 取值 |
|---------|----------------------|
| 客户（ad_customer/agent/provider） | 取选中候选项的 `corporationName` 字段值 |
| 地址（plan_visit_address） | 取选中候选项的 `poiName` 字段值 |
| 门店（store） | 取选中候选项的 `poiId` 字段值（数字 ID，不是名称） |
| customer_type | 取选中候选项的枚举值（`新客`/`老客`） |

> **禁止把序号 `"1"` 当 `raw` 提交**；**禁止把 `"北京市"` 等部分字段当 `raw` 提交**。

## [创建成功后按钮交互]


### follow_up_action — 用户点击"当前计划签到"

前端下发 `payload.value="check-in-current-plan"` + `payload.visitPlanId`。直接触发 `visit-checkin` skill，跳过查找步骤，直接构建签到卡。

### follow_up_action — 用户点击"添加陪访人信息"

前端下发 `payload.value="add-companion"`。**payload 不含 `visitPlanId`**，需从 `a2uiCardData.visitPlanId` 取。

**处理流程**：
1. 调 `search-accompany-user --keyword ""` 搜索陪访人；若用户已提供关键词直接用关键词搜索
2. 展示候选列表（`userName` + `department`），支持多选
3. 用户回复序号 → 从搜索结果取出对应用户，构造 JSON 对象（只提取 `avatar`/`userName`/`userCode` 3 个字段，禁止传 `userId`/`department`/`position`）
4. 调 `add-accompany-user --plan-id <visitPlanId> --users '<JSON数组>'`
5. 成功 → "已成功添加陪访人：XX"；失败 → 输出错误提示

> 此流程与创建 FSM 完全无关：禁止调 `state`/`batch-resolve`/`execute`。
